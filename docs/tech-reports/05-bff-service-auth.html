Echo Blog 通信経路

バックエンドを「誰でも呼べる API」から「BFF だけが呼べる内部 API」に変え、レートリミットを利用者ごとに効かせた後の構成です。リクエストがどこを通り、どこで誰が検証されるかをまとめます。

Markdown 版: 05-bff-service-auth.md（内容を変えるときは両方を更新する）。公開リポジトリのため、GCP のプロジェクト ID は <backend-project> と表記しています。

Cloud Run 2 サービス（別プロジェクト） 直接アクセス 403 BFF 経由 200 レートリミット：利用者の IP 単位

全体像

Cloud Run は 2 つです。画面と BFF（/api/*）は同じ Next.js アプリで、Cloud Run どうしの通信は「① → ②」の 1 本だけです。この区間を ID トークンで保護しています。

認証は 2 段

役割の違う 2 つの認証が、別のレイヤで動きます。Authorization ヘッダはサービス間、Cookie は利用者に使うので、同じリクエストに両方が乗っても衝突しません。

クライアント IP を信頼できる理由

X-Client-IP は誰でも書けるただのヘッダです。それでも信頼できるのは、次の 4 つが順につながっているからです。どれか 1 つが崩れると成り立ちません。

  1. ブラウザ

    偽装できるのは X-Forwarded-For の左側だけ。右端は Google のフロントエンドが接続元の IP を追加する（ドメインマッピングで公開しており、ロードバランサは挟んでいない）。

  2. BFF

    右端だけを使って X-Client-IP を作る。IP として解釈できない値なら付けない。

  3. Cloud Run IAM

    バックエンドには BFF しか到達できない。だから X-Client-IP を書けるのは BFF だけになる。

  4. バックエンド

    TRUST_CLIENT_IP_HEADER=true のときだけヘッダを信頼する。値が不正なら BFF の IP として数える（値を変えても回避できない）。

切り替え当日、3 が崩れていました。サービスの invoker IAM チェックが無効（invoker-iam-disabled）のままで、allUsers を外しても誰でも呼べました。そのため「非公開化」と「ヘッダの信頼」は、deploy.yml の同じ gcloud run deploy で必ずまとめて設定します。

ページを開いたときのリクエスト

ページはすべてクライアントコンポーネントです。まず画面の器（HTML・JS）を取り、そのあとブラウザがデータを /api/* から取ります。/api/* の 1 リクエストにつき、① から ② へのリクエストが 1 本出ます。トップページでは 5 本前後です。

sequenceDiagram
    participant B as ブラウザ
    participant F as Cloud Run ①（Next.js）
    participant M as メタデータサーバー
    participant E as Cloud Run ②（Echo）
    B->>F: GET /（HTML・JS・CSS）
    F-->>B: 画面の器
    Note over B: JS が画面を組み立てる
    par データ取得（並行）
        B->>F: GET /api/blogs
    and
        B->>F: GET /api/blogs/categories ほか
    end
    F->>M: ID トークン（期限 5 分前までキャッシュ）
    M-->>F: JWT
    F->>E: GET /api/blogs（Bearer + X-Client-IP）
    E-->>F: 200 JSON
    F-->>B: 200 JSON

運用メモ

  • コンソールでバックエンドを「公開」に戻さない。invoker の IAM チェックが無効になり、IAM のバインディングに関係なく誰でも呼べるようになる。
  • --no-allow-unauthenticated・--invoker-iam-check・TRUST_CLIENT_IP_HEADER=true は 1 つのデプロイで揃えて変える。片方だけ変えると、偽装でレートリミットを回避できる状態になる。
  • レートリミットのカウントはインスタンスのメモリにある。最大 3 インスタンスなので、実効上限は最大 3 倍まで緩む。
  • BFF の ID トークンが取れないと、BFF は 500 {"error":"Backend authentication failed"} を返す。フロントのログに Failed to obtain ID token for backend が出る。

BFF 経由が 401 / 403 になったときの切り戻し

IAM チェックを無効にして一時的に公開へ戻す。数秒で効く。TRUST_CLIENT_IP_HEADER=true が残るので、公開のまま放置せず、原因を直して --invoker-iam-check に戻す。

gcloud run services update echo-blog-app \
  --project <backend-project> --region asia-northeast1 \
  --no-invoker-iam-check

状態の確認

invoker-iam-disabled が出力されなければ、IAM チェックは有効。

gcloud run services describe echo-blog-app \
  --project <backend-project> --region asia-northeast1 \
  --format='value(metadata.annotations)' | tr ';' '\n' | grep invoker
